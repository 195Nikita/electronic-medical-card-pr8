# Электронная медицинская карта

Практическая работа № 8, МДК.02.02, вариант 2. Борцов Никита.

Учебный проект: перечень артефактов, правила разработки и архитектурное решение для интеграции с лабораториями. Репозиторий не содержит реальных медицинских данных.

## Фактическое состояние

Основная ветка: `main`. Рабочая ветка: `feature/lab-results-import`.
Материалы из рабочей ветки перенесены в main с сохранением истории Git. Основная ветка содержит архитектурную схему, API-контракт, код политики доступа, тесты, карточку задачи и ADR-001 в этом README.
Публичный репозиторий: https://github.com/195Nikita/electronic-medical-card-pr8
Обе ветки сохранены на GitHub. Перенос выполнен через fast-forward без Pull Request и внешнего ревью. Серверная защита main не настроена.

## Проверка

Требуется .NET SDK 8 или новее и доступ к NuGet при первом восстановлении зависимостей.

```sh
dotnet test tests/MedicalRecord.Tests.csproj
git branch --all
git log --oneline --all --graph
```

Тесты проверяют учебную политику доступа. Обработчик загрузки результатов, OAuth-сервер, база данных и сетевой обмен FHIR в этой работе не реализованы; соответствующие требования зафиксированы в контракте и ADR.

## Протокол работы с Git

В этой работе фактически создана ветка `feature/lab-results-import`. Номер Issue не включён: Issue в удалённом сервисе не создан.
Новые функции разрабатываются в `feature/<название>`, исправления - в `bugfix/<название>`.
Основная ветка main содержит подготовленные материалы и проверенные модульные тесты. Для дальнейшей командной работы следует включить защиту main и создавать Pull Request из рабочей ветки.

Условия слияния: успешный `dotnet test`, проверка контракта, отсутствие секретов и реальных данных, устранение блокирующих замечаний и одобрение одного рецензента. На локальном репозитории эти условия являются правилами команды и не обеспечиваются сервером.

### Чек-лист Code Review

1. Проверить аутентификацию и авторизацию, валидацию входных данных и аудит; исключить медицинские данные из технических логов.
2. Проверить идентификаторы пациента и назначения, отсутствие дублей при повторной доставке, обработку ошибок и тайм-аутов.
3. Проверить архитектурные границы, позитивные и негативные тесты и совместимость API-контракта.

## ADR-001: FHIR R4 для интеграции с лабораториями

Статус: принято как проектное решение; полная интеграция ещё не реализована.

### Проблема

Лаборатории передают результаты в разных форматах. Необходимо связать результат с пациентом и назначением, проверять структуру сообщений и предотвращать повторное сохранение.

### Решение

Использовать HL7 FHIR R4 и REST. Пациента представлять ресурсом Patient, назначение - ServiceRequest, результат - DiagnosticReport и Observation. В контракте этого репозитория передача результатов описана как FHIR Bundle. Конкретные обязательные элементы и системы кодирования должны закрепляться в согласованном профиле интеграции.

Для рабочего развёртывания требуются TLS, OAuth 2.0 со scope lab-results.write, проверка прав, атомарное сохранение и Idempotency-Key. Повтор с тем же ключом и содержимым возвращает исходный результат, с другим содержимым - конфликт. Внутреннюю модель отделить от FHIR преобразованием на границе сервиса. Операции доступа фиксировать в защищённом аудите.

### Отклонённая альтернатива

Собственный JSON-формат для каждой лаборатории. Он проще для первого подключения, но создаёт несовместимые контракты и увеличивает объём преобразований и сопровождения.

### Последствия

Нужны версионирование профиля, таблицы соответствия справочников и контрактные тесты. Подключение новой лаборатории должно включать проверку совместимости. Использование FHIR само по себе не заменяет настройку безопасности и проверку корректности данных.
